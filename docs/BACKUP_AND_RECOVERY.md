# Система резервного копирования и восстановления (Backup & DR)

**Проект:** V-Portal / ARV — B2B SaaS для создания AR-контента
**Область:** PostgreSQL, медиафайлы, Redis, конфигурация и секреты, инфраструктура
**Статус:** P0 и P1 реализованы в коде (см. §13.2 и §14); P2 частично — только поля `backup_history`
**Дата:** 2026-09-14

---

## 1. Цели и целевые показатели

| Показатель | Цель | Комментарий |
|---|---|---|
| **RPO** (допустимая потеря данных) | **24 ч** (базово) / **5 мин** (при включённом WAL-архивировании) | AR-контент создаётся нечасто; 24 ч приемлемо как база |
| **RTO** (время восстановления) | **≤ 2 ч** — БД; **≤ 6 ч** — полный контур с медиа | Зависит от объёма медиа и скорости канала |
| **Глубина хранения** | 3 года (годовые копии) | Совпадает с типичным сроком жизни рекламных материалов |
| **Проверка восстановлением** | ежемесячно, автоматически | Единственное доказательство работоспособности бэкапа |
| **Целевая модель** | **3-2-1-1-0** | 3 копии, 2 типа носителей, 1 off-site, 1 offline/immutable, 0 непроверенных |

**3-2-1-1-0** расшифровка применительно к ARV:

- **3 копии** — продовые данные + локальная копия + off-site копия;
- **2 типа носителей** — SSD/HDD сервера и объектное хранилище (S3);
- **1 off-site** — обязательно у другого провайдера, не у того, где лежит прод;
- **1 offline/immutable** — копия, которую нельзя удалить/перезаписать (object lock или выключенный диск);
- **0 ошибок** — ни одна копия не считается валидной без проверки целостности и учебного восстановления.

## 2. Инвентаризация данных: что подлежит бэкапу

### 2.1 Классификация

| Класс | Данные | Где лежит | Критичность | Восстановимость |
|---|---|---|---|---|
| **A1** | База данных PostgreSQL (14 таблиц) | volume `postgres_data` / `/var/lib/postgresql/data` | 🔴 Критично | **Не восстанавливается** — единственный источник |
| **A2** | Оригиналы медиа: загруженные фото и видео | `/opt/arv/storage/VertexAR/{project_slug}/{order_number}/` | 🔴 Критично | **Не восстанавливается** — пользователь их не перезальёт |
| **A3** | Секреты и конфигурация: `.env`, ключи, SSL-сертификаты | `/opt/arv/app/.env`, `/etc/letsencrypt/`, `deploy/` | 🔴 Критично | **Не восстанавливается** |
| **B** | Производные медиа: `marker.mind/.png`, `qr_code.png`, `thumbnail.*`, `photo_enhanced.png` | рядом с оригиналами, `thumbnails/{company_id}/` | 🟡 Средне | ✅ Регенерируются из A2 |
| **C** | Redis: JWT-чёрный список, `user_revoked`, 2FA-pending/attempts, счётчики rate-limit, кэш QR, OAuth-state | volume `redis_data` | 🟢 Низко | ✅ Полностью эфемерны, пересоздаются |
| **D** | Код приложения | git (`github.com/fegerV/ARV`) | — | ✅ Уже версионируется |

### 2.2 Почему именно так

**A1 — база.** Содержит то, что нельзя воспроизвести: `users.hashed_password` (PBKDF2), `companies.yandex_disk_token` (Fernet-шифрование), `storage_connections` (креды хранилищ), `system_settings` (включая настройки безопасности), всю структуру `companies → projects → ar_content → videos`.

> ⚠️ **Важное следствие:** дамп БД **сам по себе недостаточен** для полноценного восстановления. OAuth-токены Yandex Disk зашифрованы `TOKEN_ENCRYPTION_KEY`, а JWT подписываются `SECRET_KEY`. Без класса **A3** восстановленная БД будет содержать нерасшифровываемые токены, и пользователи потеряют доступ к своим хранилищам. Поэтому A3 — обязательная часть схемы, а не «приятное дополнение».

**A2 — оригиналы медиа.** Это самый объёмный и самый «невосполнимый» ресурс. Пользователь загрузил фото картины и видео — если они потеряны, AR-метка физически не восстановима (нужно заново фотографировать и заново печатать QR). Ограничения из конфигурации: фото ≤ 10 МБ, видео ≤ 100 МБ.

**B — производные.** `marker.mind`, `qr_code.png`, `thumbnail.*`, `photo_enhanced.png` детерминированно генерируются из оригинала. Их включение в бэкап ускоряет восстановление (не нужно гонять OpenCV/MindAR по всему архиву), но не критично. Решение: **включать в недельный полный бэкап, исключать из ежедневных инкрементов** — так мы экономим трафик и место, сохраняя ускоренное восстановление.

**C — Redis.** Все ключи либо имеют TTL, либо безопасно теряются:
- `jwt_blacklist:*`, `user_revoked:*` — потеря означает лишь то, что отозванные токены снова станут валидны до истечения TTL (≤ 24 ч);
- `2fa:pending:*` — пользователь запросит код заново;
- `oauth_state:*` — OAuth-флоу перезапускается;
- счётчики rate-limit — сбрасываются, это не инцидент безопасности.

Бэкапить Redis **не нужно**, но нужно зафиксировать это решение в runbook, чтобы при восстановлении не искать «потерянные» данные.

**D — код.** Уже в git. Единственное требование: перед каждым деплоем фиксировать в `backup_history`/runbook актуальный commit SHA, чтобы восстановление шло на совместимую версию схемы.

```
                        │        ПРОДОВЫЙ СЕРВЕР (arv)         │
                        │                                      │
   ┌────────────┐       │  ┌────────────────┐                  │

   └────────────┘       │  ┌────────────────┐  │  ┌──────────┐ │

   │  (медиа)   │       │  └────────────────┘  │  └────┬─────┘ │

                                                       │
              ┌────────────────────────────────────────┼─────────────────────┐
              │                                        ▼                     │
              │   ┌──────────────────┐   ┌──────────────────┐   ┌──────────┐ │
              │   │ S3 «primary»     │   │ S3 «secondary»   │   │  HDD     │ │
              │   │ Yandex Object    │   │ Backblaze B2 /   │   │ offline  │ │
              │   │ Storage          │   │ Selectel / NAS   │   │ (сейф)   │ │
              │   │ + Object Lock    │   │ (иной провайдер) │   │ 1×мес    │ │
              │   └──────────────────┘   └──────────────────┘   └──────────┘ │
              │        off-site №1           off-site №2          offline    │
              └─────────────────────────────────────────────────────────────┘

  Ежедневно ─▶ инкремент       Еженедельно ─▶ полный + проверка
  Ежемесячно ─▶ восстановление в тестовую БД (restore drill)
```

### Ключевое решение: **два независимых off-site провайдера**

Медиа прода **уже хранится на Yandex Disk**. Если бэкапы складывать только туда же (как сейчас делает `BackupService`), то компрометация одного Yandex-аккаунта или сбой провайдера уничтожает **и прод, и бэкап одновременно**. Это классическая коррелированная ошибка. Поэтому:

- **off-site №1** — Yandex Object Storage (быстро, дёшево, в регионе);
- **off-site №2** — **обязательно другой провайдер** (Backblaze B2 / Selectel / собственный NAS в другом помещении).

## 4. Периодичность и расписание

Все задания запускаются **systemd-таймерами на хосте**, а не внутри процесса приложения. Причина: если приложение упало или зависло, планировщик внутри него умрёт вместе с ним — и бэкапы молча остановятся. Встроенный APScheduler (`app/core/scheduler.py`) остаётся для ручного/админского запуска, но не является основой.

| # | Задание | Расписание | Тип | Куда | Хранение |
|---|---|---|---|---|---|
| 1 | **PostgreSQL dump** | `03:00` ежедневно | полный (`pg_dump -Fc`) | staging → S3 №1 + №2 | GFS: 7д/4н/12м/3г |
| 2 | **WAL-архивирование** (опция) | непрерывно | archive | S3 №1 | 7 дней |
| 3 | **Медиа (оригиналы)** | `03:30` ежедневно | инкремент (restic) | S3 №1 | GFS (см. §8) |
| 4 | **Медиа (производные)** | `04:00` вс | полный (restic) | S3 №1 | 4 недели |
| 5 | **Секреты и конфиг** | `04:30` вс | tar + age | S3 №2 (отдельный репозиторий) | 12 недель + при каждой ротации |
| 6 | **Проверка целостности** | `05:00` вс | `restic check` + `pg_restore --list` | — | отчёт в `backup_history` |
| 7 | **Restore drill** | `06:00` 1-го числа | восстановление в тестовую БД | — | отчёт + алерт при провале |
| 8 | **Offline-копия** | 1-го числа, вручную | полный архив на HDD | сейф | 3 месяца (ротация 3 дисков) |
| 9 | **Синхронизация на S3 №2** | после №1, №3 | репликация | S3 №2 | как у источника |

### Обоснование выбора времени

- **Ночь (03:00–06:00)** — минимум пользовательской активности, AR-контент почти не создаётся, `pg_dump` не конкурирует за I/O с продом.
- **Разнесение по 30 минут** — задания не накладываются: `pg_dump` и `restic` оба интенсивно читают диск, одновременный запуск даст деградацию прод-отклика.
- **Суббота — окно обслуживания** — тяжёлые операции (полный бэкап производных, проверка целостности) вынесены на выходные, когда нагрузка минимальна.
- **Ежедневный инкремент медиа** — новые AR-материалы появляются в течение дня; суточный RPO покрывает потерю максимум одного дня загрузок.

## 5. Способ и место хранения

### 5.1 Три уровня

| Уровень | Расположение | Назначение | Время жизни |
|---|---|---|---|
| **Staging** | `/var/backups/arv` (локальный диск сервера) | точка сборки перед отправкой; быстрый доступ для drill | 48 часов |
| **Off-site №1** | S3-совместимое (Yandex Object Storage), bucket `arv-backups` | основная удалённая копия | GFS |
| **Off-site №2** | другой провайдер (Backblaze B2 / Selectel) | защита от отказа/компрометации провайдера №1 | GFS |
| **Offline** | внешний HDD, сейф/другой адрес | защита от ransomware и компрометации аккаунтов | 3 месяца |

### 5.2 Инструменты

| Данные | Инструмент | Почему |
|---|---|---|
| PostgreSQL | `pg_dump -Fc` + `age` | custom-format: сжатие, параллельное (`pg_restore -j`) и выборочное восстановление |
| Медиа | `restic` | дедупликация, инкременты, шифрование на клиенте, снапшоты, `check` |
| Секреты | `tar` + `age` | простой, предсказуемый, не требует агента |
| WAL | `pg_receivewal` / `archive_command` | PITR (point-in-time recovery) |

### 5.3 Почему restic, а не rsync/tar

- **Дедупликация.** Производные медиа (thumbnail разных размеров, `photo_enhanced`) частично дублируют друг друга — restic хранит блоки однократно, экономя 30–50 % объёма.
- **Шифрование «из коробки».** AES-256-CTR + Poly1305-AES, ключ через scrypt. Не нужно изобретать схему шифрования самому.
- **Снапшоты и GFS.** `restic forget --keep-daily 7 --keep-weekly 4 ...` — ротация одной командой, без ручного перебора файлов.
- **`restic check --read-data-subset=N%`** — встроенная проверка целостности с чтением реальных данных, обнаруживает bit rot.
- **Любой backend.** Локальный диск, S3, B2, SFTP, rclone — можно сменить провайдера без переделки схемы.

### 5.4 Защита от удаления

Бэкап, который может удалить скомпрометированное приложение, — не бэкап. Меры:

1. **Раздельные учётные данные.** Приложение пишет бэкапы под отдельным ключом с правами `PutObject`/`ListBucket` **без** `DeleteObject`. Удаление — только отдельным ключом оператора.
2. **Object Lock (WORM)** на bucket S3 №1: `--object-lock-mode COMPLIANCE`, срок 30 дней. Даже владелец аккаунта не удалит копию досрочно.
3. **Versioning** на bucket — защита от перезаписи.
4. Бэкап-скрипты запускаются от отдельного пользователя `backup`, а не от `arv`.

## 6. Шифрование и управление ключами

### 6.1 Что и как шифруется

| Слой | Механизм | Ключ |
|---|---|---|
| В покое — медиа (restic) | AES-256-CTR + Poly1305-AES, ключ через scrypt | restic password |
| В покое — дампы БД и секреты | `age` (X25519) | age private key |
| При передаче | TLS 1.2/1.3 (HTTPS к S3) | — |
| На диске сервера (staging) | LUKS на разделе `/var/backups` | LUKS passphrase |

### 6.2 Обязательные требования

- **Дамп БД шифруется всегда.** Даже gzip-дамп содержит `users.hashed_password` и `storage_connections`. Утечка дампа без шифрования = утечка базы хешей паролей.
- **Ключи НЕ хранятся на продовом сервере.** Если злоумышленник получил root на `arv`, он не должен получить и ключи шифрования — иначе он прочитает все бэкапы.
- **Секреты (A3) — в отдельный репозиторий с другим ключом.** Иначе получится «сейф, ключ от которого приклеен к дверце»: дамп БД и ключ `TOKEN_ENCRYPTION_KEY` в одном архиве.

### 6.3 Где хранить ключи

| Копия | Место | Доступ |
|---|---|---|
| Основная | менеджер паролей (Bitwarden/Vaultwarden, отдельный проект «ARV Backup») | 2–3 оператора, 2FA |
| Резервная | распечатанный ключ в запечатанном конверте в сейфе | 2 подписи для вскрытия |
| Аварийная | `age`-ключ разбит по схеме **Shamir 3-of-5** между руководителями | вскрытие при потере основной и резервной |

### 6.4 Ротация ключей

- **Плановая** — раз в 12 месяцев: `restic key add` → новый ключ → `restic key remove` старый; перевыпуск age-ключей с полным перешифрованием архива.
- **Внеплановая** — немедленно при увольнении оператора с доступом, при подозрении на компрометацию.
- Ротация **не** требует пересоздавать бэкапы: restic перешифровывает только метаданные ключа; для age — выполняется `age -d | age -e` по архиву (разово, в окно обслуживания).

## 7. Проверка целостности

Три уровня — от дешёвого к дорогому:

| Уровень | Метод | Частота | Что ловит |
|---|---|---|---|
| **1. Контрольная сумма** | SHA-256 при создании, сверка при выгрузке | каждая копия | повреждение при передаче/записи |
| **2. Структурная проверка** | `pg_restore --list dump` (валидность архива), `restic check` (метаданные) | еженедельно | обрыв дампа, битые индексы репозитория |
| **3. Чтение данных** | `restic check --read-data-subset=5%` (полный `--read-data` — раз в месяц) | еженедельно / ежемесячно | bit rot на носителе |
| **4. Restore drill** | восстановление в тестовую БД + проверки консистентности | ежемесячно | **всё остальное** |

### 7.1 Что именно проверяет restore drill

Восстановление идёт в **отдельную** БД `vertex_ar_restore_test` на том же или тестовом хосте, прод не затрагивается:

```
1. pg_restore -j4 -d vertex_ar_restore_test dump.sql.gz
2. alembic upgrade head                # схема совпадает с кодом
3. SELECT count(*) по ключевым таблицам → сверить с ожидаемым трендом
4. Проверить referential integrity: ar_content.project_id → projects.id
5. Проверить, что company_id у всех записей не NULL
6. Расшифровать один companies.yandex_disk_token ключом из A3
   → доказательство, что секреты восстановимы
7. Восстановить 10 случайных AR-контентов из медиа-снапшота
   → проверить, что photo/marker/qr на месте и открываются
8. DROP DATABASE vertex_ar_restore_test
```

Шаг 6 — критичен: он проверяет не только БД, но и то, что связка **«дамп + ключ»** действительно даёт рабочие OAuth-токены. Без него можно месяцами хранить бэкапы, которые не восстановятся в рабочее состояние.

### 7.2 Расширение модели данных

`backup_history` уже содержит `status`, `size_bytes`, `checksum`, `yd_path`, `error_message`, `trigger`. Предлагается добавить:

| Поле | Назначение |
|---|---|
| `backup_type` | `db` / `media` / `secrets` / `config` |
| `target` | `s3-primary` / `s3-secondary` / `offline` |
| `verified_at` | когда последний раз проверялась |
| `verification_status` | `ok` / `checksum_mismatch` / `restore_failed` |
| `restore_tested_at` | дата последнего успешного drill |
| `duration_seconds` | длительность (для тренда деградации) |
| `app_commit` | SHA коммита — на какую версию схемы восстанавливать |
| `encrypted` | bool, подтверждение шифрования |

## 8. Глубина хранения и стратегия ротации

### 8.1 GFS (Grandfather-Father-Son)

| Уровень | Хранить | Покрытие |
|---|---|---|
| **Daily** (ежедневно) | 7 | последняя неделя |
| **Weekly** (воскресенье) | 4 | последний месяц |
| **Monthly** (1-е число) | 12 | последний год |
| **Yearly** (1 января) | 3 | 3 года |
| **Итого** | **~26 снапшотов** | — |

Для restic — одной командой:

```bash
restic forget \
  --keep-daily 7 --keep-weekly 4 --keep-monthly 12 --keep-yearly 3 \
  --prune
```

Для дампов БД (файлы) — та же логика через теги в имени: `db_YYYYMMDD_HHMMSS.sql.gz.age`; ротация скриптом по GFS-правилу.

### 8.2 Почему GFS, а не «30 последних копий»

Текущая реализация (`_rotate_backups` в `app/services/backup_service.py`) хранит `max_copies` последних копий + `retention_days`. Проблема: при таком правиле **невозможно** откатиться на состояние «месяц назад» — все старые копии уже вытеснены. GFS сохраняет редкие долгоживущие точки, что критично для:

- расследования инцидента, замеченного не сразу (например, порча данных, обнаруженная через 3 недели);
- требований аудита/регуляторов;
- восстановления после длительной логической ошибки (массовое удаление, сбойная миграция).

### 8.3 Offline-ротация

Три внешних диска, по одному в месяц:
- диск A — в сейфе (текущий месяц);
- диск B — у ответственного дома (прошлый месяц);
- диск C — перезаписывается (позапрошлый месяц).

Это даёт защиту от ransomware: даже при полной компрометации всех сетевых учёток остаётся копия, физически отключённая от сети.

### 8.4 Оценка объёма

```
S_db    ≈ 50–200 МБ  (gzip дампа, зависит от числа записей)
S_media ≈ N × (10 МБ фото + 100 МБ видео + ~15 МБ производных)
          где N — число AR-контентов
```

Пример: 1000 AR-контентов ≈ **125 ГБ** оригиналов. С дедупликацией restic и сжатием — порядка **60–80 ГБ**. Умножаем на ~1.5 (GFS-глубина с инкрементами) → **~100–120 ГБ** на off-site. Бюджет объектного хранилища холодного класса — порядка нескольких долларов в месяц.

### 9.2 Правила алертинга

| Приоритет | Условие | Смысл |
|---|---|---|
| 🔴 **Critical** | `backup_age_seconds > 26h` | суточный бэкап не выполнялся |
| 🔴 **Critical** | 2 подряд `status=failed` | системная поломка |
| 🔴 **Critical** | `verify_status == 0` | бэкап повреждён |
| 🔴 **Critical** | restore drill провален | бэкап не восстанавливается |
| 🟠 **Warning** | размер упал > 30 % от медианы за 7 дней | признак усечённого/пустого дампа |
| 🟠 **Warning** | `duration` вырос в 3× | деградация, приближение к таймауту |
| 🟠 **Warning** | свободное место на staging < 20 % | следующий бэкап упадёт |
| 🟡 **Info** | ротация удалила > 50 % снапшотов | проверить настройки retention |

### 9.3 Dead-man's-switch — обязательный элемент

Все метрики выше **бесполезны**, если сам сервер лёг: метрики просто перестанут поступать, и алерт не сработает (Prometheus увидит «нет данных», а не «проблема»). Поэтому:

- после каждого успешного бэкапа скрипт отправляет heartbeat на **внешний** сервис (healthchecks.io / Uptime Kuma);
- если heartbeat не пришёл в течение 26 часов — внешний сервис шлёт алерт.

Это единственный способ поймать отказ «тихо умершего» сервера или остановившегося таймера.

### 9.4 Каналы оповещения

- **Telegram** — через уже реализованный `AlertService.send_telegram_alerts()` (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_CHAT_ID`);
- **E-mail** — `send_admin_email()`;
- Каналы **не должны** зависеть от продового приложения: если упал `arv`, алерт из самого `arv` не уйдёт. Дублировать через внешний сервис.

## 11. Итоговая схема (сводка)

| Параметр | Решение |
|---|---|
| **Что бэкапим** | PostgreSQL (A1) + оригиналы медиа (A2) + секреты/конфиг (A3). Redis — не бэкапим. Производные — только в недельный полный |
| **Как часто** | БД и медиа — ежедневно 03:00/03:30; полный — еженедельно; проверка — еженедельно; drill — ежемесячно |
| **Чем** | `pg_dump -Fc` + `age`; `restic` для медиа; `tar + age` для секретов |
| **Куда** | staging (48 ч) → S3 №1 (Yandex) + S3 №2 (другой провайдер) + офлайн-HDD ежемесячно |
| **Глубина** | GFS: 7 daily / 4 weekly / 12 monthly / 3 yearly (~26 точек) |
| **Шифрование** | restic (AES-256-CTR+Poly1305), age (X25519), TLS в транзите; ключи вне прод-сервера, Shamir 3-of-5 |
| **Целостность** | SHA-256 → `restic check` → `--read-data` → **ежемесячный restore drill** |
| **Мониторинг** | Prometheus-метрики + алерты в Telegram/e-mail + **внешний dead-man's-switch** |
| **RPO / RTO** | 24 ч (5 мин с WAL) / ≤ 2 ч (БД), ≤ 6 ч (полный) |

## 12. Обоснование ключевых решений

**1. Почему медиа бэкапится, хотя «файлы же можно перезалить»?**
Нельзя. Оригинал фото — это физическая картина, которую клиент сфотографировал один раз. Повторная загрузка невозможна без повторной фотосессии. При этом именно медиа составляет ~99 % объёма данных. Текущая реализация бэкапит **только БД** — то есть восстанавливает «оглавление» без «книги».

**2. Почему два off-site провайдера, а не один?**
Продовое хранилище медиа — Yandex Disk. Бэкап на том же провайдере не защищает от: блокировки аккаунта, компрометации OAuth-токена, регионального сбоя, ошибки биллинга. Требование «второй провайдер» превращает коррелированный отказ в независимый.

**3. Почему restic, а не собственный скрипт с tar+gzip?**
Собственный скрипт придётся писать с нуля: инкременты, дедупликация, шифрование, ротация, проверка целостности, поддержка нескольких backend'ов. restic даёт всё это проверенным, зрелым кодом. Уже существующий `BackupService` показывает, во что превращается ручная реализация: нет шифрования, нет инкрементов, нет проверки восстановлением, ротация не умеет GFS.

**4. Почему systemd-таймеры, а не APScheduler в приложении?**
Бэкап — функция инфраструктуры, а не бизнес-логики. Он должен работать, даже если приложение не стартовало (например, из-за ошибки в коде или БД) — а именно в этот момент бэкап нужнее всего. Внутренний планировщик остаётся как удобство для админа.

**5. Почему обязателен restore drill?**
Бэкап, который ни разу не восстанавливали, — это гипотеза, а не бэкап. Типичные «тихие» отказы: дамп создаётся, но пустой; архив валиден, но ключ шифрования потерян; БД восстанавливается, но секреты — нет, и OAuth-токены нечитаемы. Только сквозной drill «дамп + ключ + медиа → рабочая система» выявляет эти проблемы **до** реального инцидента.

**6. Почему дамп шифруется, хотя это «внутренние данные»?**
Дамп содержит `users.hashed_password` и `storage_connections`. Даже PBKDF2-хеши — чувствительные данные (подвержены offline-перебору слабых паролей). Незашифрованный дамп в объектном хранилище — это фактически утечка базы учётных данных.

**7. Почему GFS, а не «30 последних копий»?**
Инциденты обнаруживаются с задержкой. Порча данных, замеченная через 3 недели, требует точки восстановления месячной давности — при правиле «30 последних» её уже не существует. GFS даёт и оперативную (ежедневную), и историческую (годовую) глубину при умеренном объёме.

**8. Почему offline-копия на диске?**
Ransomware и компрометация облачных учёток — основной сценарий, против которого сетевые бэкапы бессильны. Физически отключённый диск — единственная копия, недостижимая для атакующего с доступом к сети.

## 14. Приложения

### 14.1 Реализованная структура

Логика бэкапа живёт в Python (покрыта тестами), хостовые скрипты — тонкие
обёртки вокруг неё (блокировка, права на staging, коды возврата). Дублировать
логику в bash не нужно: её пришлось бы тестировать дважды.

| Компонент | Файл | Назначение |
|---|---|---|
| Дамп БД | `app/services/backup_service.py` | `pg_dump -Fc -Z0` → gzip → `age` → primary + secondary → GFS |
| Медиа | `app/services/media_backup_service.py` | restic `backup` / `forget --prune` / `check --read-data-subset` |
| Восстановление | `app/services/restore_service.py` | материализация, `pg_restore --list`, drill, restore в отдельную БД |
| Ротация | `app/services/backup_rotation.py` | чистые функции GFS-отбора (без БД и ФС) |
| Метрики | `app/services/backup_metrics.py` | серии `arv_backup_*` для Prometheus |
| Heartbeat | `app/utils/heartbeat.py` | внешний dead-man's-switch |
| Команды | `app/utils/command.py` | единый запуск внешних бинарников с таймаутом |
| CLI | `app/cli/backup.py` | `db`, `media`, `secrets`, `verify`, `drill`, `restore`, `status`, `notify` |
| Скрипты | `deploy/backup/*.sh` | `flock`, staging, коды возврата |
| Таймеры | `deploy/systemd/arv-backup-*.{service,timer}` | расписание + `OnFailure=` |
| Миграция | `alembic/versions/20260914_1400_backup_verification.py` | поля верификации в `backup_history` |

> Имя артефакта осталось прежним — `backup_<ts>.sql.gz` (и `.sql.gz.age` при
> шифровании). Это сознательное решение: на это имя завязаны UI бэкапов и
> операционные инструкции. Формат внутри — custom (`-Fc`), поэтому файл
> восстанавливается только через `pg_restore`; сжатие делает gzip (`-Z0`
> отключает внутреннее сжатие pg_dump, чтобы не сжимать дважды).

### 14.2 CLI

```bash
cd /opt/arv/app

# Ежедневные задания (их вызывают таймеры)
python -m app.cli.backup db
python -m app.cli.backup media
python -m app.cli.backup secrets

# Проверка: SHA-256 + pg_restore --list

# Drill: восстановление в одноразовую БД и подсчёт таблиц
python -m app.cli.backup drill

# Восстановление (только в отдельную БД; продовая отвергается кодом)
python -m app.cli.backup restore 42 --target-db vertex_ar_recovered

# Состояние: последний запуск по каждому типу, возраст, верификация
python -m app.cli.backup status
```

### 14.3 Установка таймеров

```bash
cd /opt/arv/app
sudo install -m 0755 deploy/backup/*.sh /opt/arv/app/deploy/backup/
sudo install -m 0644 deploy/systemd/arv-backup-* /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now \
    arv-backup-db.timer arv-backup-media.timer arv-backup-secrets.timer \
    arv-backup-verify.timer arv-backup-drill.timer

systemctl list-timers 'arv-backup-*'
```

Расписание (все таймеры с `Persistent=true`):

| Таймер | Когда | Что делает |
|---|---|---|
| `arv-backup-db.timer` | ежедневно 03:00 UTC | дамп БД |
| `arv-backup-media.timer` | ежедневно 03:30 UTC | restic-снапшот медиа |
| `arv-backup-secrets.timer` | вс 04:00 UTC | `.env` + TLS + `deploy/` |
| `arv-backup-verify.timer` | вс 05:00 UTC | контрольные суммы + `pg_restore --list` |
| `arv-backup-drill.timer` | 1-е число 06:00 UTC | восстановление в одноразовую БД |

`Persistent=true` — не деталь: без него выключенный в 03:00 сервер молча
пропускает сутки. Медиа-задание смещено на 03:30 от БД-задания, потому что оба
конкурируют за диск и за канал в объектное хранилище.

При сбое любого задания systemd запускает `arv-backup-alert@%n.service`, который
вызывает `python -m app.cli.backup notify`. Алерт отправляется **отдельным
процессом**, а не из веб-приложения: приложение может быть как раз тем, что
сломалось, и алерт из него не уйдёт.

### 14.4 Полезные команды

```bash
# Список снапшотов
restic snapshots

# Точечное восстановление одного AR-контента
restic restore latest --target /tmp/restore \
  --include /opt/arv/storage/VertexAR/my-project/ORD-123

# Проверка дампа без восстановления
pg_restore --list db_20260914.dump | head -50

# Восстановление с параллелизмом
pg_restore -j4 -d vertex_ar db_20260914.dump

# PITR (при включённом WAL-архивировании)
restore_command = 'cp /var/lib/postgresql/wal_archive/%f %p'
recovery_target_time = '2026-09-14 02:55:00+00'
```
