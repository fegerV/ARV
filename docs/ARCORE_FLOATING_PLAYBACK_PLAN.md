# ARCore Floating Playback Plan

## Цель

Добавить в Android-приложение V-Portal новый режим воспроизведения для ARCore Augmented Images:

- когда маркер находится в кадре, видео остаётся привязанным к изображению;
- когда маркер теряется, видео не останавливается и продолжает воспроизводиться по центру экрана;
- когда маркер снова появляется, видео повторно привязывается к маркеру без перезапуска playback.

Изменение относится только к Android ARCore viewer. Веб-AR в проекте не используется.

## Текущий статус

На текущей реализации приложение использует ARCore Augmented Images и Media3 ExoPlayer:

- `android/app/src/main/java/ru/neuroimagen/arviewer/ar/ArRenderer.kt`
- `android/app/src/main/java/ru/neuroimagen/arviewer/VPortalActivity.kt`

Текущее поведение:

- видео рисуется только при `TrackingState.TRACKING`;
- при потере маркера приложение отключает звук и ставит плеер на паузу;
- после повторного наведения воспроизведение продолжается только после возврата tracking.

## Новое поведение

### Пользовательский сценарий

1. Пользователь наводит камеру на маркер.
2. ARCore распознаёт изображение.
3. Видео запускается и отображается поверх маркера.
4. Пользователь уводит камеру от маркера.
5. Видео не останавливается, а продолжает проигрываться в центре экрана.
6. Пользователь снова наводит камеру на маркер.
7. Видео возвращается на маркер в текущем моменте playback.

### Бизнес-ценность

- более мягкий UX при кратковременной потере трекинга;
- меньше ощущения, что приложение "сломалось", если маркер временно ушёл из кадра;
- более предсказуемое поведение для промо- и презентационных сценариев.

## Техническая концепция

### 1. Разделить playback и способ рендера

Сейчас потеря маркера одновременно влияет на:

- воспроизведение ExoPlayer;
- отрисовку видео-квада.

Новая версия должна разделить эти обязанности:

- ExoPlayer продолжает playback независимо от видимости маркера;
- renderer самостоятельно выбирает, где рисовать видео: на маркере или в центре экрана.

### 2. Ввести два режима отрисовки

- `MARKER_ATTACHED`: видео рисуется по `AugmentedImage.centerPose`
- `SCREEN_CENTER_FLOATING`: видео рисуется фиксированно перед камерой

### 3. Поведение при смене tracking state

- `TRACKING`: перейти в `MARKER_ATTACHED`
- нет `TRACKING`, но видео готово: перейти в `SCREEN_CENTER_FLOATING`
- нет видео или renderer ещё не готов: не рисовать quad

### 4. Центрирование видео

В floating-режиме видео должно:

- оставаться по центру экрана;
- иметь фиксированный размер, визуально комфортный на телефоне;
- не зависеть от последней pose маркера;
- не дёргаться при движении камеры.

Практически это означает отрисовку квада в координатах камеры или через фиксированную pose перед камерой.

## Предлагаемая реализация

### Шаг 1. Обновить поведение player state

Файл: `VPortalActivity.kt`

Текущее поведение при потере маркера:

- `player.volume = 0f`
- `player.playWhenReady = false`

Новое поведение:

- не вызывать pause через `playWhenReady = false`;
- отдельно решать, нужно ли глушить звук при потере маркера;
- передавать renderer событие о смене режима отображения.

Рекомендация для первой итерации:

- playback не останавливать;
- звук оставлять включённым только если это соответствует текущему UX приложения;
- если есть риск нежелательного звука, временно оставлять mute при `marker lost`, но не ставить плеер на паузу.

### Шаг 2. Добавить режим floating render

Файл: `ArRenderer.kt`

Нужно:

- хранить текущий render mode;
- отслеживать наличие tracking как и сейчас;
- при отсутствии tracking, но при готовом видео, рисовать floating quad;
- сохранить текущее поведение screen recording и photo capture.

### Шаг 3. Расширить `VideoQuadRenderer`

Файл: `VideoQuadRenderer.kt`

Нужно добавить второй способ draw:

- draw on tracked image pose;
- draw in screen-centered floating mode.

Для floating mode нужно подобрать:

- фиксированную дистанцию до квада;
- ширину/высоту;
- допустимый aspect ratio для текущего видео.

### Шаг 4. Стабилизировать переходы

Чтобы избежать мигания при плохом tracking, добавить один из механизмов:

- debounce перед переходом в floating mode, например 200-500 мс;
- или удержание предыдущего режима на короткое время;
- или фильтрация быстрых чередований `TRACKING` / `PAUSED` / `STOPPED`.

Минимальная версия может выйти без debounce, но это повышает риск визуального "дребезга".

### Шаг 5. Обновить пользовательские подсказки

При необходимости добавить текстовое поведение:

- если маркер потерян, можно показывать краткую подсказку "Наведите камеру обратно на изображение, чтобы вернуть привязку";
- не перекрывать само floating video агрессивными оверлеями.

## Ограничения и допущения

- Это не world-lock и не сохранение объекта в реальном пространстве после потери маркера.
- После потери `AugmentedImage` видео будет отображаться как camera-centered overlay.
- Возврат на маркер будет происходить скачком, без гарантии плавного morph-перехода.
- Для первой версии не требуется менять серверный API или формат манифеста.

## Риски

### UX-риски

- пользователь может не понять, почему видео "отлипло" от реального объекта;
- при резком возврате на маркер возможен заметный snap-переход.

### Технические риски

- неправильный расчёт floating pose может дать искажённый размер видео;
- возможен конфликт с записью AR-видео, если overlay рисуется иным путём;
- частые смены tracking state могут вызвать мерцание между режимами.

### Производительность

- дополнительная логика рендера минимальна;
- при отсутствии паузы ExoPlayer будет продолжать декодирование, что немного увеличит расход батареи и нагрев в сравнении с текущей логикой.

## План тестирования

### Функциональные тесты

1. Видео стартует после распознавания маркера.
2. При потере маркера видео не останавливается.
3. При потере маркера видео появляется по центру экрана.
4. При повторном распознавании видео возвращается на маркер.
5. Возврат происходит без перезапуска ролика.
6. При завершении видео и автопереходе на следующий ролик новый ролик ведёт себя так же корректно.

### Негативные тесты

1. Маркер быстро появляется и исчезает.
2. Видео ещё не готово, а tracking уже потерян.
3. Устройство с низкой производительностью.
4. Смена ориентации экрана, если поддерживается текущим экраном.

### Регрессионные тесты

1. Deep link `https://.../view/{unique_id}`.
2. Custom scheme `arv://view/{unique_id}`.
3. Offline после первого успешного просмотра.
4. Screenshot через PixelCopy.
5. AR recording, если функция активна в текущей сборке.
6. Обработка ошибок `invalid_unique_id`, `subscription_expired`, `no_playable_video`, отсутствия ARCore.

### Критерии приёмки

Изменение считается готовым, если:

1. На поддерживаемом ARCore-устройстве видео продолжает playback после потери маркера не менее 30 секунд.
2. Floating-видео остаётся визуально центрированным и без критичных искажений.
3. При повторном наведении на маркер видео снова прикрепляется к изображению в пределах 1 секунды после восстановления tracking.
4. Не возникает сбоев screenshot/recording сценариев.
5. Не появляется деградации в загрузке манифеста, кэше и deep links.

## Что можно проверить уже сейчас

Без внесения кода уже доступна предварительная техническая проверка:

- сборка Android-модуля;
- прогон unit tests, если они есть и не завязаны на устройство;
- проверка, что текущая логика действительно паузит player при потере tracking.

Полная валидация нового поведения невозможна без:

- внесения изменений в Android-код;
- установки на физическое устройство с ARCore;
- ручной проверки AR-сцены.
